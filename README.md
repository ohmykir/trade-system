## Trade System

Бэкенд для торговой системы. Пользователи выставляют заявки на покупку и/или 
продажу ценных бумаг и/или валютных пар. Система сопоставляет встречные заявки
и генерировать сделки.

### Стек

- Java 21, Spring Boot 3.5, Maven
- PostgreSQL 15
- Flyway, Hibernate(validate)
- Docker Compose

### Запуск
```
docker compose up --build
```
Приложение: http://localhost:8080;
База создается автоматически, миграции применяются на старте.

### API

Базовый путь: /api/v1

| Метод  | Путь                       | Описание                                                                          |
|--------|----------------------------|-----------------------------------------------------------------------------------|
| POST   | /orders                    | Выставить заявку. Заголовок Idempotency-Key обязателен                            |
| PUT    | /orders/{id}               | Изменить цену и количество. Idempotency-Key обязателен                            |
| DELETE | /orders/{id}               | Отменить заявку                                                                   |
| GET    | /orders                    | Реестр заявок (фильтры accountId, seccode, type, status,<br/>from, to, пагинация) |
| GET    | /trades                    | Реестр сделок (фильтры accountId, seccode, from, to, пагинация)                   |
| GET    | /quotes/{seccode}?depth=10 | Текущие котировки: стакан по инструменту                                          |

### Дополнения к модели данных

- У Account добавлено поле reserved для резерва средств под активные заявки на покупку
- У Order добавлены:
  - Ключ идемпотентности idempotencyKey;
  - filledQuantity для частичного исполнения заявки
  - createdAt для времени создания
- У Trade добавлены ссылки на заявки на покупку и продажу, породившие сделку и время исполнения

### Принятые допущения по бизнес-логике

- Только лимитные заявки.
- Учитывается только денежная часть сделки в валюте инструмента. 
Передача бумаг и базовой валюты не моделируется, наличие бумаг у продавца не проверяется.
- Заявки одного счета могут исполняться друг против друга, в этом случае баланс счета не меняется.
- Пользователей и аутентификации нет, проверки владельца заявки нет.
- При изменении заявки теряется приоритет.
- Ключи идемпотентности хранятся бессрочно.
- Счета и инструменты заводятся миграциями, API для пополнения баланса нет.

### Решения по бизнес-логике

1. Выставление заявок: проверяется существование счета и инструмента, цена и количество положительны,
цена кратна минимальному шагу, средств для покупки достаточно. Под покупку средства резервируются.
2. Редактирование/Отмена: изменение реализовано как отмена старой и создание новой заявки в одной транзакции.
Отмена проверяет статус заявки, отменяется только активная заявка.
3. Исполнение заявок: сопоставление запускается синхронно в той же транзакции, что и создание/изменение заявки.
Приоритет цена-время: покупатель получает самые дешевые продажи, продавец самые дорогие покупки, 
при равной цене исполняется заявка, поданная раньше.
4. Котировки: стакан строится агрегацией активных заявок по ценовым уровням: цена, суммарное количество лотов и
число заявок. Обе стороны читаются из одного снимка данных, чтобы не было пересечения.
5. Реестры: фильтры не обязательные и комбинируются.

Дополнительно:

6. Введен ключ идемпотентности для создания и изменения заявки. Передается в заголовке и сохраняется в заявке. 
Уникальна на пару (account_id, idempotency_key).

7. Конкурентность: две заявки не могут исполняться одновременно по одному инструменту, поэтому берется
пессимистичная блокировка на строку инструмента, потом на счета. Чтение блокировок не берет.


P.S.: Тестовые данные есть, на тесты времени не хватило.
